Decision

The 5 × 5 live matrix is diagnostic-only because destination, first-use UI, asset state, and initial cache state differed. The repository record is doc/performance/renderer-stage-1-decision.md.

Delivered

Write the benchmark contract

Add a short specification under doc/performance/. Define scenario identity, viewer build, graphics settings, resolution, present mode, cache state, camera timing, warm-up, capture duration, repeat count, invalid-run rules, output schema, and privacy rules.

  • Start with 30 seconds of warm-up, 120 seconds of capture, and five repeats per configuration.
  • Record cold-cache and warm-cache runs separately. Never average them together.
  • Disable VSync and frame caps for throughput runs. Test frame pacing separately with the normal present settings.
  • Reject runs with incomplete asset loading, unexpected simulator events, power throttling, wrong GPU selection, or changed visual features.
  • Predeclare the meaningful-change threshold. It must exceed both 1 ms at p95 and three times the run-to-run noise measured for that scenario.
ProofA reviewer can reproduce the exact protocol without asking the author which settings or samples count.
 

Add versioned scenario manifests

Add machine-readable scenario files under scripts/perf/scenarios/. Use session settings or existing command-line options so benchmark runs do not alter a normal user profile.

  • Store region or captured-workload identity, camera position and path, duration, cache mode, graphics settings, and expected feature flags.
  • Record environmental observations that the viewer cannot control, including avatar count, active objects, simulator ping, and asset completeness.
  • Do not store login credentials. Keep using an operator-supplied credentials file where noninteractive login is required.
  • Hash the effective settings and manifest into every result so unlike runs cannot compare silently.
ProofA dry run prints the complete viewer command and effective settings without launching or reading secrets into output.
 

Split CPU frame time into useful phases

Extend the existing LLPerfStats and frame recording path. Capture geometry creation and rebuild, partition processing, culling, state sorting, render submission, UI/HUD, swap, texture work, shader compilation, idle work, and the total frame.

  • Keep scopes mutually understandable. Document known nesting so totals are not added twice.
  • Record per-thread traces when Tracy is available. Always capture per-core utilization outside the viewer.
  • Separate CPU time spent issuing GL work from CPU time blocked inside queries, uploads, fences, readbacks, or present.
  • Make counters benchmark-only or cheap enough to leave disabled in normal builds.
ProofEvery bad p95 frame can be assigned to scene preparation, API submission, a blocking wait, UI, present, or an explicit unclassified remainder.
 

Add GPU and resource evidence without creating stalls

Use GPU timestamps or external captures for pass time. Record draw calls, batch size, triangles, shader and pipeline changes, texture uploads, upload bytes, readbacks, fence waits, shader compile time, allocated texture memory, and available memory where the platform reports it.

  • Do not force blocking query results in the normal benchmark loop.
  • Keep the existing per-shader Frame Profile as a separate diagnostic run because query collection can perturb timing.
  • Preserve the current AMD driver safeguards that disable problematic benchmark and occlusion queries.
  • Correlate CPU and GPU traces. A long GL call may be waiting on earlier GPU work.
ProofThe result distinguishes GPU pass cost, submission overhead, present wait, shader work, resource churn, and explicit synchronization.
 

Complete the result context and remove identifying data

Extend benchmark output with commit, build type, OS, CPU model, logical core count, GPU, driver, OpenGL vendor/renderer/version, context profile, resolution, backend label, feature flags, settings hash, cache state, scenario, and run number.

  • Do not copy the current raw machine identifier, account identity, parcel name, or private region data into checked-in results.
  • Use an operator-assigned hardware label for repeated measurements.
  • Version the JSON schema and reject incompatible comparisons.
ProofA checked-in fixture contains enough context for comparison and no account, machine, or location identifier that should remain private.
 

Build the runner and reporter

Add a small runner and report tool under scripts/perf/. Reuse the existing frame-profile utilities and perfbot_run.py where their behavior fits. Keep the new result format separate from the one-frame shader profile.

  • Support manifest validation, dry run, repeated runs, timeout, result collection, and a failure reason.
  • Emit raw versioned JSON plus a compact CSV or Markdown summary.
  • Report median, p95, p99, worst frame, 1 percent low, run-to-run range, and counter totals.
  • Compare only matching scenario, settings hash, cache mode, resolution, feature set, and build type unless the operator overrides the guard explicitly.
ProofUnit fixtures cover valid data, mismatched contexts, missing samples, invalid runs, percentile calculations, and privacy filtering.
 

Run the workload suite

Collect the minimum matrix below. Run release builds without validation for performance. Collect separate diagnostic traces with profiling or GPU validation enabled.

  • Randomize comparison order when practical so temperature and background activity do not favor one configuration.
  • Use the same viewer commit and scenario manifest for native GL and Zink.
  • Record advertised extensions, limits, feature masks, shader level, and screenshot hashes before interpreting a Zink result.
  • Repeat any result that crosses the meaningful-change threshold on a second machine or driver version from the same class.
ProofEvery reported delta links to five valid raw runs and a visual/settings equivalence check.
 

Write the Stage 1 decision record

Check in a concise report under doc/performance/. Rank the dominant p95 and p99 contributors per hardware class. State what the evidence supports, what it does not support, and which Stage 2 scope follows.

  • Separate platform-modernization reasons from measured performance reasons.
  • List cheap current-OpenGL fixes even if the project continues toward Vulkan.
  • Record discarded runs and why they were invalid.
  • Keep raw heavyweight traces as build or test artifacts. Check in small summaries and representative fixtures only.

Active and detailed

Stage 2: capture the affected-hardware regression

The next commit must turn the reported slowdown into controlled evidence. It adds workload validity and investigation artifacts, not a performance fix, renderer abstraction, compatibility-layer deployment, or Vulkan code.

In scope

  • A deterministic or tightly controlled benchmark workload
  • Automatic placement, camera, UI, asset, and environment validity gates
  • One affected newer system and a matched older control
  • Requested and actual OpenGL context negotiation evidence
  • Per-core CPU and external GPU/API diagnostic captures
  • A diagnosis that selects one Stage 3 scope

Out of scope

  • Optimizing a suspected bottleneck before it is reproduced
  • Adding an RHI, Vulkan device, shader conversion, or MoltenVK
  • Shipping Zink or another compatibility layer to users
  • Expanding the full hardware matrix before the affected pair works
  • Committing raw captures, screenshots, credentials, or location identity
  • Changing a live region or production service
Required input. Execution needs access to one machine that exhibits the newer-hardware regression and one older control on the same platform, or reproducible reports detailed enough to reserve those machines. If that pair is unavailable, Stage 2 remains uncommitted rather than substituting the RX 480 reference host.
 

Choose and freeze one workload

Use a team-controlled benchmark scene, a reproducible local/captured workload if the viewer supports one, or a tightly controlled parcel with a fixed camera. The choice must be reachable without mutating a normal profile and repeatable on both hardware classes.

  • Give the workload a privacy-safe versioned identifier; keep the actual location operator-supplied.
  • Specify login flow, placement, camera transform, window size, graphics settings, cache preparation, warm-up, duration, and expected feature flags.
  • Define the expected object/avatar envelope and the asset-settled condition before collecting performance samples.
  • Capture one approved native-OpenGL visual reference outside Git and record only its non-reversible comparison fingerprint.
ProofTwo consecutive launches reach the same camera and accepted visual/environment fingerprint without manual cleanup.
 

Make workload validity machine-checkable

Extend the manifest, exporter, and runner only where the Stage 1 invalid runs showed a gap. A run must fail before reporting performance when placement, first-use UI, asset state, or scene population is wrong.

  • Wait for the expected world/teleport state and camera checksum rather than assuming the startup URL succeeded.
  • Require benchmark UI state and reject unexpected modal or first-use floaters.
  • Require a stable texture/upload and pending-download window before warm capture; preserve a separate cold-streaming contract.
  • Record privacy-safe scene/environment fingerprints and rejection reasons in the result.
  • Add fixtures for wrong destination, unsettled assets, unexpected UI, changed population, and a valid settled run.
ProofThe failure modes observed in Stage 1 become rejected fixtures and cannot produce a comparison report.
 

Trace OpenGL context negotiation

Record the requested context attributes, creation attempts, fallback path, and final advertised profile on the affected platform. Keep requested settings distinct from driver-reported results.

  • Test the viewer's normal context request and its existing core-profile option where the platform supports both.
  • Record GL version/profile, vendor, renderer, driver, limits, extension hash, feature mask, shader level, and context creation failures.
  • On Linux, retain native GL versus Zink as a secondary diagnostic only after native runs are stable and visually equivalent.
  • Do not infer a core or compatibility profile from a preference flag.
ProofLogs and result metadata explain exactly which context was requested, which fallback occurred, and which context rendered every measured run.
 

Run the affected pair

Use the same commit, workload version, settings, resolution, and operating-system class on the affected newer hardware and older control. Prefer ReleaseOS builds and stable power/thermal conditions.

  • Collect the full 30-second warm-up, 120-second capture, five-repeat matrix for the normal context on both machines.
  • Run alternate core/compatibility or Zink configurations only when capability and visual gates match.
  • Randomize comparison order where practical and record per-core utilization, clocks, power mode, and throttling observations.
  • Repeat a threshold-crossing result on a second driver or same-class machine before generalizing it.
ProofEach reported delta links to five valid raw runs per configuration and separates regression evidence from machine-to-machine noise.
 

Capture one CPU/API/GPU diagnostic set

After the steady runs pass, collect separate perturbing traces for the most important affected and control configurations. Use the platform's established tools rather than adding synchronous profiling to the frame loop.

  • Use Tracy or an equivalent thread trace plus operating-system per-core sampling to expose main-thread saturation and waits.
  • Use RenderDoc, Nsight Graphics, Radeon GPU Profiler, PIX, apitrace, or the closest vendor tool for GPU pass time, queue idle, GL-call stalls, resource churn, and present behavior.
  • Add one coarse CPU scope only if the external trace shows that the current unclassified bucket hides the deciding cost.
  • Keep large captures in investigation storage and record tool versions, artifact hashes, and a privacy-safe summary in Git.
ProofThe same slow frame can be followed from viewer phase through thread/API behavior to GPU or present cost without a profiling query in the steady run.
 

Classify the regression and test the hypothesis

Rank p95 and p99 contributors and correlate them with resource counters and traces. Use the Stage 1 threshold: a p95 change must exceed both 1 ms and three times measured run-to-run noise.

  • Distinguish scene preparation, GL submission, driver synchronization, present, resource churn, and GPU pass cost.
  • State whether requested versus actual context selection changes the result.
  • Use a reversible diagnostic toggle or capture observation to test the leading explanation; do not ship the fix in this stage.
  • Report null or unstable results plainly and do not promote average FPS as a substitute.
ProofThe diagnosis identifies one bounded next action, or explicitly shows that the report cannot yet be reproduced.
 

Write the decision and replan Stage 3

Check in a small privacy-safe summary, update this same rolling plan, and expand exactly one Stage 3. Preserve raw runs and captures outside Git.

  • Select a current-OpenGL correction when the trace identifies a bounded bottleneck.
  • Select the dual-backend contract spike only when evidence or a separately approved platform requirement justifies it.
  • Treat Zink as a production candidate only after native-equivalent visuals, features, stability, packaging, and support costs are measured.
  • Record unavailable matrix cells and limit the claim to tested hardware.
ProofThe updated plan names Stage 2 actuals, one evidence-backed Stage 3, its exit gates, and one reviewable commit boundary.

Stage 2 risk register

Affected hardware is unavailable

The reference RX 480 does not exhibit the reported newer-hardware regression and cannot answer the question.

Control. Make the affected/control pair an entry gate. Do not commit a diagnosis from substitute hardware.

The live world changes between runs

Simulator activity, avatars, asset delivery, and occlusion history can swamp the renderer delta.

Control. Prefer a controlled workload; otherwise fingerprint placement, scene, UI, and asset state and reject changed conditions automatically.

Instrumentation changes the result

GL query reads and fine-grained logging can introduce the stalls being measured.

Control. Separate low-overhead benchmark counters from diagnostic traces. Measure instrumentation overhead and preserve driver query guards.

Zink changes more than one variable

Extensions, shader variants, feature masks, compiler behavior, and memory management may differ.

Control. Compare capabilities and output before timing. Phrase the result as evidence about the broader driver/API path.

Aggregate CPU use hides the main thread

A saturated core can look like low process utilization on a modern CPU.

Control. Capture per-thread traces and per-core utilization. Correlate them with GPU idle and pass timestamps.

Benchmark artifacts leak identity

The current profile context can include a machine identifier, region, and parcel information.

Control. Define a benchmark-safe context, use operator-assigned labels, add redaction tests, and review fixtures before commit.

The stage becomes a renderer cleanup

It will be tempting to fix the first suspicious wait or state transition found in a trace.

Control. Record the correction as the Stage 3 candidate. Keep Stage 2 diagnostic so the baseline remains trustworthy.

Hardware gaps invite broad claims

The team may not have every affected GPU and platform available.

Control. Publish matrix gaps beside the conclusion. Do not infer Windows or macOS behavior from a Linux Zink result.
